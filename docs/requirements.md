# training2 业务需求

本项目实现用于学习 REST API 的小型商城，包含管理端和买家端。本文将 README 和实施计划中的功能细化为可实现、可验证的规则。以下新增细节是本次启动采用的默认设计，可在对应数据库和 API 契约实现前调整。

## 范围和身份

- 管理员：登录后注册商品、查看管理商品列表。
- 访客：搜索商品、查看商品及当前库存。
- 买家：登录后创建、查看、确认和取消自己的订单。
- 管理员身份通过经过验证的 Cognito 用户组 `admin` 判断；订单所有者通过 token 的 `sub` 判断，不能信任请求中的用户 ID。
- 注册账号、支付、配送、商品编辑删除、订单草稿编辑、独立购物车和管理订单页面不在初期范围内。开发账号通过初始化脚本准备。

## 商品和输入规则

| 字段 | 规则 |
| --- | --- |
| 商品代码 | 去除首尾空白并转成大写；1 到 32 字符；仅 ASCII 字母、数字、连字符和下划线；规范化后全局唯一 |
| 商品名称 | 去除首尾空白；1 到 100 个 Unicode 字符 |
| 商品说明 | 纯文本；可为空；最多 2000 个 Unicode 字符 |
| 价格 | 日元 JPY，整数，0 到 100000000；不接受小数、数字字符串、NaN 或无穷大 |
| 库存 | 整数，0 到 1000000 |
| 订单明细数量 | 整数，1 到 1000 |

名称和说明均以纯文本显示。价格不计算额外税费或运费。字段长度按 Unicode 码点计数，各层保持一致；未知输入字段拒绝。商品注册成功返回 201；重复代码返回 409；其他输入违规返回 400。DB 对唯一代码、金额非负、库存范围和数量范围提供约束。

## 商品搜索和列表

商品代码按规范化后的完全一致匹配，商品名按不区分大小写的字面子串匹配；`%` 和 `_` 不作为通配符。两个条件同时提供时采用 AND。空白条件等同未提供条件，没有条件时显示全部商品。

管理列表与公开搜索均按商品代码升序，使用 page/pageSize 分页。page 从 1 开始，pageSize 默认 20，范围 1 到 100。超过末页返回空数组，不报错。公开响应包含代码、名称、说明、JPY 价格和当前库存，不包含内部认证信息。

库存显示是查询时的快照，不构成预留。最终是否可购买由确认订单时的事务检查决定。

## 订单创建和金额

- 每单包含 1 到 50 种不同商品；使用商品 ID 和数量提交，不接受客户端价格、总额或所有者。
- 同一商品重复出现返回 400，不自动合并；不存在的商品返回 404。
- 创建时保存商品代码、名称和单价快照；总额由服务器按保存单价乘数量后求和，最大为 5000000000000 日元，仍在 JavaScript 安全整数范围内。
- 创建时不检查是否足够购买、不扣库存，可以为库存不足商品创建草稿。确认时必须重新检查库存。
- 创建页面重新查询所选商品库存，数量输入即时限制为 1 到 min(库存,1000)，整数；库存为零时不能选择或提交。该限制仅改善页面交互，不把库存快照当作预留，API 创建草稿仍不扣库存。
- 创建页面提供“取消商品选择”，确认后清空全部选择、数量及创建 key 并返回商品页；关闭确认框或选择保留不清空。“继续选购”保留当前选择。
- 草稿明细不提供修改 API；需要修改时取消旧草稿、重新创建。
- 创建操作必须提供 UUID 格式的 `Idempotency-Key`。以买家 sub 和 key 唯一关联订单，并保存规范化输入用于比较。key 不过期、不复用。
- 同 key 和相同输入重试返回原订单（200），不能生成第二单；同 key 不同输入返回 409。首次创建返回 201。并发重试也遵守此规则。
- 规范化比较先按商品 ID 排序；只改变明细顺序视为相同输入。

订单详情按状态显示操作：草稿显示确认与取消；已确认隐藏确认，仅保留右下方柔和红色取消按钮，与金额右侧对齐。取消请求期间隐藏两个按钮并显示处理中；成功后不再展示操作，失败时恢复可用操作并提示重试。

## 订单状态和库存

| 当前状态 | 操作 | 结果 | 库存变化 |
| --- | --- | --- | --- |
| draft | 确认 | confirmed | 扣减全部明细数量 |
| confirmed | 再次确认 | 返回当前订单，200 | 不重复扣减 |
| cancelled | 确认 | 409 状态冲突 | 不变 |
| draft | 取消 | cancelled | 不变 |
| confirmed | 取消 | cancelled | 返还全部明细数量一次 |
| cancelled | 再次取消 | 返回当前订单，200 | 不重复返还 |

不存在的订单返回 404。属于其他买家的订单统一返回 404，避免暴露订单是否存在。管理身份不自动授予访问他人订单的权限。

确认和取消必须先锁定订单行，确认时再按商品 ID 升序锁定涉及的商品行。确认、取消对同一订单竞争时按取得锁的顺序执行：取消先完成，则确认失败；确认先完成，则取消返还库存。最终状态与库存必须一致。

在同一数据库事务中检查状态、更新全部库存并保存新状态。任何明细不足都返回 409，整个操作回滚。库存从不为负数。同一商品库存为 1，两笔数量为 1 的订单同时确认时，恰好一笔成功，另一笔库存不足。

在明确回滚的死锁或序列化失败时，服务器最多重试整个事务 2 次（共 3 次尝试，短暂随机退避）；仍失败返回 503。不能重试已经提交且结果不明的任意业务操作，客户端使用上述幂等规则重试。

## 操作和响应

| 操作 | 身份 | 正常响应 | 主要失败 |
| --- | --- | --- | --- |
| 注册商品 | 管理员 | 201 商品 | 400 输入；401 未认证；403 无管理权限；409 重复代码 |
| 管理商品列表 | 管理员 | 200 分页结果 | 400 分页；401；403 |
| 搜索商品和查询库存 | 任何人 | 200 分页结果 | 400 搜索或分页输入 |
| 创建订单 | 登录用户 | 201 新订单或 200 原订单 | 400 输入；401；404 商品；409 幂等 key 冲突 |
| 查看订单 | 所有者 | 200 订单 | 400 ID；401；404 不存在或非所有者 |
| 确认订单 | 所有者 | 200 订单 | 400 ID；401；404；409 库存或状态冲突；503 竞争重试耗尽 |
| 取消订单 | 所有者 | 200 订单 | 400 ID；401；404；503 竞争重试耗尽 |

ID 使用 UUID。错误统一为 `{ "error": { "code": "...", "message": "...", "requestId": "..." } }`，输入错误可附带字段路径，不回显密码或 token。内部异常返回 500，不泄漏数据库、堆栈或内部响应。契约细节在 Step5 固化。

认证验证覆盖签名、过期时间、issuer、access token 用途和 client ID。浏览器权限显示只负责体验，服务端仍执行认证、管理权限和订单所有者检查。

## 受理标准

所有功能必须覆盖正常输入、异常输入、权限和库存变化，详见 [验收场景](acceptance-scenarios.md)。并发测试使用实际 PostgreSQL 的独立连接；单靠 mock 或逐次调用不能证明排他控制正确。


## 商品登记页面与界面语言

2026-10-14：买家端和管理端的界面、状态/错误文案与组件默认文案统一为日文，采用用户提供的公司SVG与柔和蓝色。商品登记表单即时限制价格为非负整数（上限沿用API契约），初始库存为0～2000的整数；这是登记页面的暂定输入限制，API/数据库已有库存范围不收窄，避免影响既有数据及客户端。用户录入的商品内容不自动翻译；开发内置示例使用日文。

## 自动更新与确认优先顺序（2026-10-14）

成功确认先获得库存，选择或草稿创建不预留；并发确认不承诺点击时间或服务器请求受理时间的严格FIFO。真实独立连接竞争时只允许库存足够的事务成功，其余409且不扣库存。

买家/管理列表使用提交后数据库通知和SSE自动刷新缓存。首次加载可显示占位，后台刷新保留商品行、数量输入、搜索、分页和滚动。断线提示并自动重连；重连/回到页面时补查快照，30秒轮询兜底。通知仅含公开商品变更提示，不含订单或用户信息。

库存变少不静默更改已选数量，提示调整并禁用创建；零库存禁止选择和创建。草稿详情自动检查库存，不足或无法验证时禁止确认，最终确认事务始终重新校验。取消已确认订单返还库存并通知其他页面。

## 统一订单入口（2026-10-14）

买家导航仅一个「注文」入口，沿用/orders/new。无所选商品时显示本人所有订单及未确定/已确定/已取消状态筛选，最新订单优先并分页；无历史显示空白和创建按钮，有历史列表底部显示创建新订单。创建新订单进入商品选择，选择后同一入口显示数量表单。订单与所选商品缓存不同，已提交订单不因选择缓存清空而消失。

未确定显示确认/取消，库存不足禁止确认；已确定仅取消；已取消无操作。列表和详情的确认/取消都先弹确认框，返回/关闭不发请求，确认后再提交；库存与状态变更刷新列表。列表API只从JWT sub确定所有者，禁止查询他人订单，不接受请求指定owner。
